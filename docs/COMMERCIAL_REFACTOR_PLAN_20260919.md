# DWGC2E 商用化重构与全面优化计划

- **评审日期**：2026-09-19
- **项目**：DWGC2E / DWG Translator
- **目标**：从“功能可用”提升到“可长期维护、可运营、可交付、可扩展的商用桌面软件”。
- **本计划范围**：桌面 APP、Cloudflare Worker 后台、AI Provider 路由、安装包、安全边界、测试与发布。
- **明确约束**：配色本阶段暂不调整；优先保证 1280×720、1440×900、1920×1080 的常用体验；不把大量时间投入极小窗口；正式运行版本始终是 `D:\DWGC2E\release`。

---

## 1. 结论：不是继续零散修按钮，而是做一次“商用化专项”

目前项目已经具备比较完整的功能底座：

- WPF / .NET 8 桌面端；
- Core、App、CAD 插件分层；
- Worker API、D1、账号、设备、术语库、任务恢复；
- AI Provider 配置、加密凭据、优先级、权重、重试、熔断、故障转移的初版基础；
- 构建、安装、回滚、UI smoke、Core 测试、Worker 测试已经形成流水线。

但目前的问题集中在“产品层”和“边界层”：

1. 页面虽然能完成操作，但缺少统一的信息架构，导致用户需要猜测下一步。
2. XAML 和 ViewModel 中存在较多高耦合、固定尺寸、局部补丁式布局，容易出现按钮裁切、空白过多、列宽异常、滚动层级失控。
3. 任务、翻译、导出、恢复、重试已经有不少逻辑，但还需要统一成清晰的状态机与用户可理解的错误模型。
4. AI 路由本地源码已有实现，但本地源码、D1 migration、线上 Worker 三者尚未形成可验证的部署闭环。
5. 客户端历史上存在提示词/运行资源路径，需要继续确保正式包不包含高价值 Prompt、Provider 密钥、后台密钥和真实 Provider 地址。

因此建议按 **P0 安全与上线边界 → P1 桌面信息架构 → P2 任务/数据可靠性 → P3 AI 路由运营化 → P4 安装包与客户端防护 → P5 商用验收** 的顺序推进，而不是继续在每个页面单独打补丁。

## 2. 当前审查结论

### 2.1 已确认并已修复的真实问题

#### 设置页 Grid 行定义缺失

`D:\DWGC2E\src\DwgTranslator.App\Views\Pages\SettingsPage.xaml` 中多个配置区域原先只有列定义，没有明确的 `RowDefinitions`。标题、输入框、开关落在同一默认行，造成标题和字段垂直重叠。这是实际的结构性布局 bug，不是截图误差。

当前已补充行定义，并将标题、内容、环境信息、保存栏分到明确行中。设置页标题重叠问题已经消失。

#### 保存栏与表单宽度问题

设置页底部保存栏已改为绑定表单实际宽度，并加入可达性验证。当前 smoke 已验证宽度一致、按钮可达。由于内部 ScrollViewer 内容偏移，保存栏与表单的 X 坐标仍可进一步统一，但不再属于“按钮无法使用”的阻断问题。

#### 翻译页、批量任务页、术语库页的一轮布局修复

已经完成：

- 常用按钮增加 `MinWidth` / `MinHeight` 和 Tooltip；
- 操作列、状态列、进度列扩大，避免文字和按钮裁切；
- DataGrid 支持排序、列宽调整、整行/扩展选择；
- 翻译页无效空白、拖拽空状态高度、右侧设置区宽度已收紧；
- 输出目录改为路径展示加两行操作按钮；
- 抽屉、设置区增加滚轮边界传递；
- 删除高频 `LayoutUpdated` 高度调整，避免布局抖动和重复测量。

这些是第一轮稳定性修复，下一轮仍需从统一页面骨架和信息密度角度重构，而不是继续逐个控件加宽。

### 2.2 当前架构风险

#### ViewModel 过重、职责分散

`D:\DWGC2E\src\DwgTranslator.App\ViewModels` 下的 `MainViewModel.*.cs` 虽然通过 partial 拆分了文件，但本质仍是一个承担导航、设置、账户、任务、导入导出、术语库、更新、环境检查、支付和 UI 状态的超大聚合对象。当前已有多个 200～780 行的 partial 文件。

这会带来：

- 一个页面的改动容易影响其他页面；
- 业务规则与控件状态交叉；
- 难以为每个页面编写可独立运行的 ViewModel 测试；
- 任何异步异常、取消、页面切换都容易产生状态泄漏。

#### XAML 过于密集，局部修复成本高

部分页面使用单行压缩 XAML、多个内联 Style、复杂 DataGridTemplateColumn 和深层嵌套 Grid。能减少文件长度，但不利于定位布局问题、审查可访问性和维护列宽策略。

#### 任务存储仍以 JSON 为主

当前 `ITaskStore` 保持了可替换接口，短期可用；但商用场景下，任务、项目、导出历史、检查点、错误、重试记录逐渐增多，单文件 JSON 容易遇到锁竞争、并发写入、损坏恢复、查询能力不足等问题。应在保留兼容迁移的前提下规划 SQLite/事务型本地存储。

#### Worker“本地改了”不代表“线上生效”

`D:\DWGC2E\cf-worker\src\` 和 `D:\DWGC2E\cf-worker\wrangler.toml` 只是源码与部署配置。只有完成 D1 migration、`wrangler deploy`，并从真实远程地址读取 `/v1/version`、执行远程回归，才能确认线上版本已经生效。

当前必须把以下三件事分开记录：

1. 本地源码版本；
2. 线上 Worker build id / schema version / AI routing version；
3. APP 实际连接到的 API 地址。

## 3. P0：发布、安全与线上边界（先做，阻断商用发布）

### P0.1 建立线上 Worker 可验证部署闭环

**目标**：消除“源码已改但线上没部署”的误判。

**实施步骤**：

1. 在 `D:\DWGC2E\cf-worker` 执行完整 typecheck 和 test。
2. 检查并执行生产 D1 增量 migration，禁止用重建数据库替代 migration。
3. 通过 Cloudflare Wrangler 部署 Worker。
4. 读取线上 `/v1/version`，核对：
   - `worker_build_id`；
   - `schema_version`；
   - `deployed_at`；
   - `ai_routing_version`。
5. 用受控账号做远程回归：登录、翻译、术语库、版本、错误码、Provider probe、管理员配置读写。
6. 把线上结果写入发布记录，不能只看本地 `wrangler.toml`。

**完成标准**：线上响应的 build id 与发布记录一致；migration、部署、远程契约测试全部通过；失败时不宣称已上线。

### P0.2 彻底收紧客户端安全边界

正式 APP 必须保持：

```text
APP → Cloudflare Worker → AI Provider
```

客户端不得保存或下发：

- Provider API Key；
- Provider 真实 URL；
- Provider 权重、优先级、熔断阈值；
- 后台管理密钥；
- 可复制的正式系统 Prompt；
- 生产 D1 凭据、邮件平台密钥、支付密钥。

必须继续确保：

- Provider key 只在 Worker Secret 或 Worker 加密存储中出现；
- Prompt 只在 Worker 侧生效；
- APP 只提交结构化文本、语言对、保护标记、术语结果和请求关联信息；
- 服务器返回 `context_version`，客户端把它写进任务检查点和日志元数据；
- 日志、错误消息和诊断导出均做脱敏。

**重要安全边界**：桌面端任何资源理论上都可能被提取。单文件发布、AOT、混淆、代码签名、字符串拆分只能提高逆向成本，不能承诺“绝对不可破解”。真正有价值的 Prompt、路由规则、密钥和商业策略必须不落地客户端。

### P0.3 凭据轮换

用户本轮提供的测试账号、密码和后台临时密钥不写入仓库、不写入计划文件、不写入测试代码。本轮不把它们作为自动化测试资产。测试结束后建议立即轮换：

1. 修改测试账号密码；
2. 撤销并重新生成后台临时密钥；
3. 检查 Worker、网页端、日志和截图中是否出现过敏感字段；
4. 删除临时账号的支付、管理和调试权限；
5. 将正式测试改为最小权限、短时有效的专用账号。

## 4. P1：桌面 APP 信息架构与布局重构

### P1.1 统一页面骨架

所有一级页面统一为：

```text
PageShell
├─ PageHeader：标题 + 一句话说明 + 主操作
├─ Filter / Summary Bar：筛选、搜索、统计、批量操作
├─ MainContent：唯一主滚动面
└─ Optional Drawer / Footer：详情或保存操作
```

规则：

- 每个页面默认只有一个垂直主滚动容器；
- Drawer 内部可以滚动，但必须在边界把滚轮传给页面；
- 工具栏不参与内容滚动；
- 底部主操作始终可见或在明确的 sticky footer 中；
- 避免 Grid 内的 `Auto` 行被大内容撑开；
- 主要表格使用 `*` 作为内容列，关键字段使用有下限的固定列；
- 文本类列默认 `TextTrimming=CharacterEllipsis`，完整值用 Tooltip/详情抽屉显示；
- 不使用 `LayoutUpdated` 作为常态布局算法。

建议新增可复用控件：

- `PageShell`；
- `PageHeader`；
- `SummaryMetricBar`；
- `FilterToolbar`；
- `EmptyState`；
- `StickyActionBar`；
- `DataGridColumnPreset`；
- `DrawerHost`；
- `AsyncStateView`（Loading / Empty / Error / Ready）。

### P1.2 翻译页重构

**目标**：用户打开页面后 5 秒内知道“添加文件 → 选择语言 → 翻译 → 校对 → 导出”。

建议布局：

```text
顶部：文件数量、运行状态、整体进度、暂停/取消/重试
中部：
  左 65%：任务队列 / 图纸列表
  右 35%：翻译配置、术语、保护规则
底部：选中图纸摘要、下一步主操作
```

具体措施：

- 左侧任务列表固定显示文件名、状态、文本数、进度、错误摘要；
- 文件名列占剩余空间，路径完整值放 Tooltip；
- 状态、进度、操作列使用最小宽度，不允许被压缩到不可读；
- 将“翻译设置”和“导出设置”分成两个有标题的卡片，避免所有开关堆成一列；
- 在常用宽度下可采用双排设置：语言对、翻译模式、术语策略、保护规则等按 2 列排列；
- 右侧配置区只有在内容溢出时滚动，不让整个页面出现双滚轮；
- 导出前显示“待导出图纸数、输出目录、文件命名规则、已存在文件处理方式”；
- 对“翻译完成但未导出”明确显示下一步，不把它误认为失败；
- 对部分成功任务显示成功数/失败数，并提供“仅重试失败项”。

### P1.3 批量任务页重构

批量任务页应从“历史记录表”升级为“可运营的任务中心”：

- 顶部统计：全部、运行中、待处理、待校对、已完成、部分成功、失败、已取消；
- 筛选条：搜索文件名、状态、时间、项目、错误类型；
- 表格主列：文件名、项目、阶段、进度、结果、最后更新时间；
- 操作列只放最常用动作，次要动作进更多菜单；
- 详情抽屉显示阶段时间线、请求次数、重试次数、错误码、导出记录；
- 支持键盘 Enter 打开详情、Delete 删除已结束任务、Ctrl/Cmd+R 重试失败项；
- 导出状态与翻译状态分开，避免“翻译完成但未导出”被标为完成或失败。

### P1.4 术语库页重构

术语库核心是“快速查找、批量编辑、可解释同步”，不是展示很多空白。

- 默认列：源词、目标词、语言方向、优先级、启用、同步状态、最近命中、操作；
- 源词和目标词为弹性列，操作列保持固定最小宽度；
- 增加批量启用、批量禁用、批量删除、批量导入/导出；
- 冲突项用状态徽标和筛选器展示，不在每行隐藏关键状态；
- 编辑抽屉分为“术语内容 / 适用范围 / 优先级 / 同步信息”四区；
- 大规模词库使用虚拟化或分页，避免一次渲染大量复杂模板；
- 明确本机草稿、云端已保存、同步冲突、最近同步时间。

### P1.5 设置页重构

设置页不再按“开发者配置项列表”组织，改按用户任务组织：

1. 常规：语言、启动行为、最近项目；
2. 翻译：语言对、并发、失败策略、术语策略；
3. 文件与输出：输出目录、命名、覆盖策略、备份；
4. CAD 与环境：宿主检测、插件路径、写回策略；
5. 隐私与保护：日志保留、脱敏、网络诊断；
6. 高级：仅展示确实需要的诊断项。

每个设置项必须包含：标签、当前值、简短解释、默认值/恢复默认、校验反馈。保存栏要有明确的“未保存更改”状态，避免用户不知道改动是否已经生效。

### P1.6 滚轮、焦点和输入行为统一规范

- 统一使用 `ScrollViewer` 边界传递行为；
- DataGrid、ComboBox、TextBox 内部滚动不能吞掉页面滚轮；
- 鼠标移入表格时滚轮滚表格，表格到边界后继续滚页面；
- 触控板高分辨率滚动使用累计 delta，不只依赖单次 MouseWheel；
- 关闭 Drawer 时恢复原焦点；
- 打开详情后 Esc 关闭，Enter 执行主动作；
- 所有图标按钮提供 Tooltip 和 AutomationProperties.Name；
- 所有异步动作禁用重复点击并显示进行中状态。

## 5. P2：任务状态、数据层和操作逻辑

### P2.1 统一任务状态机

建议固定以下状态，并区分翻译阶段和导出阶段：

```text
Queued
→ Preparing
→ Extracting
→ Translating
→ ReadyForReview
→ Exporting
→ Completed
```

旁路状态：

```text
Paused / Cancelling / Cancelled / Failed / PartiallyCompleted / NeedsRecovery
```

要求：

- 所有状态变化带 `updated_at`、阶段、原因码；
- UI 不根据多个 bool 推断状态；
- 状态机拒绝非法跳转；
- 取消不等于失败；
- 部分成功保留成功检查点；
- 重试只重试失败项，不重复计费、不重译已成功项；
- 重新打开 APP 后可恢复到安全状态，并明确询问继续/放弃。

### P2.2 检查点和重试

检查点至少记录：

- 源文件路径和 hash；
- 抽取文本数量；
- 文本实体版本；
- 语言对；
- 生效术语版本；
- Worker `context_version`；
- 已完成条目 ID；
- 最近错误码和重试次数；
- 最近导出路径和导出 hash。

重试策略：

- 网络超时 / 429 / 5xx：指数退避；
- 参数、文件损坏、权限错误：不自动重试，给出修复建议；
- 连续失败达到阈值：暂停任务并提示；
- 单个 Provider 失败由 Worker 处理故障转移，APP 不感知 Provider 细节；
- 任务详情中显示“已重试 N 次”，但不暴露密钥和内部管理信息。

### P2.3 本地存储演进

短期：

- 保留 `ITaskStore` 接口和当前 JSON 兼容；
- 增加原子写入：临时文件、flush、replace、备份恢复；
- 保存失败时保留上一个有效文件；
- 把大字段（原始文本、实体快照、日志）从主任务索引中分离。

中期：

- 增加 SQLite 实现，表分为 `projects`、`tasks`、`task_items`、`checkpoints`、`exports`、`events`；
- JSON 仅作为导入/导出和迁移格式；
- 迁移必须幂等、可回滚、可诊断；
- 单用户桌面环境优先保证断电恢复和并发安全，不追求复杂服务端数据库化。

### P2.4 导出和文件安全

- 导出前检查输出目录权限、磁盘空间和目标文件占用；
- 默认不覆盖用户文件，覆盖必须显式确认；
- 使用临时文件写入，完成后原子替换；
- 每次导出记录源文件 hash、目标文件 hash、时间和模式；
- 仅允许打开“最近一次成功导出”路径，不用过时的 `OutputPath` 推断；
- 兼容旧任务时，从 `ExportHistory` 或旧 `OutputPath` 回填 `LastExportPath`。

## 6. P3：后台多模型 Provider 与负载均衡

### 6.1 用户提出的功能可以实现，而且正确位置在后台

后台可以配置多个 OpenAI-compatible Provider，例如：

- Provider 名称；
- Base URL；
- 模型名；
- API Key；
- 启用/禁用；
- 优先级；
- 权重；
- 超时；
- 最大连续失败次数；
- 熔断冷却时间；
- 温度和输出上限；
- 适用套餐、租户或任务类型。

用户在网页后台发布配置后，APP 不需要更新即可通过 Worker 使用新路由。

### 6.2 路由规则

建议明确为：

1. 先按业务场景和套餐筛选候选 Provider；
2. 按 `priority` 从高到低分组；
3. 只在最高优先级健康组内按权重选择；
4. 失败后只对可重试错误做有限次数重试；
5. 连续失败达到阈值进入熔断；
6. 熔断期间跳过该 Provider；
7. 所有候选失败时返回统一错误码和 request id；
8. 记录 Provider 级指标，但不把 Provider key、完整 URL 或 Prompt 返回客户端。

### 6.3 后台界面

新增“AI 模型与路由”后台模块：

- Provider 列表：名称、模型、优先级、权重、启用状态、健康状态、最近延迟；
- 新增/编辑 Provider：API Key 只允许写入，不能回显；
- “测试连接”只返回成功/失败、延迟、模型响应校验结果；
- 路由策略：优先级、权重、业务场景、套餐；
- Prompt 策略：草稿、发布、版本、回滚、变更原因；
- 变更历史：操作者、时间、前后版本摘要、原因；
- 发布前校验：至少一个可用 Provider、Prompt schema 正确、保护规则不丢失；
- 发布后可回滚上一版本。

### 6.4 账单、额度和审计

商用必须增加：

- 每次翻译请求的 request id；
- 用户/租户/套餐归属；
- 字符数或 token 估算；
- Provider、模型、延迟、重试次数；
- 成功/失败/部分成功；
- 预算上限和异常消耗告警；
- 不把完整 DWG 文本和 Prompt 写进普通审计日志。

### 6.5 Worker 当前状态与下一步

当前源码已经具备以下初版基础：

- Provider CRUD；
- API Key AES-GCM 加密；
- Worker Secret 引用；
- 优先级与权重；
- 稳定伪随机排序；
- 超时；
- 可重试错误识别；
- 失败计数、冷却熔断、故障转移；

这些功能现在仍应视为“代码已具备、线上是否生效待部署验证”。上线前必须补齐：

## 7. P4：安装包、发布和反逆向

### 7.1 正式包内容

正式安装包不应包含：

- `prompts` 目录；
- Provider API Key；
- 后台临时密钥；
- D1 数据库信息；
- 真实支付密钥；
- 不必要的调试符号和源码映射。

可以包含：

- APP 主程序；
- CAD 插件及其必要私有依赖；
- 不敏感的默认术语库；
- 空配置模板；
- 用户说明。

当前 `release` 目录已核对，没有 `prompts` 目录；发布校验脚本也已加入“正式包不得包含客户端 Prompt”的检查。后续要继续保持这个门禁。

### 7.2 可做的客户端加固

按成本收益排序：

1. Prompt、路由规则、密钥全部服务端化；
2. 发布包移除 PDB、测试接口、诊断密钥和样例生产地址；
3. 代码签名，防止包被替换；
4. 发布清单记录 SHA-256 和签名；
5. 对关键协议增加版本和签名校验；
6. 关键业务逻辑做适度混淆或 Native/AOT 评估；
7. Worker 做会话、设备、额度、速率和异常行为控制；
8. 日志只保留必要信息，禁止输出原文、密钥、Prompt 和完整请求体。

不建议把大量精力投入“把桌面程序做成绝对不可破解”，因为用户控制自己的设备，绝对保密不可实现。要保护的是服务端资产和商业规则。

### 7.3 正式发布规则

每次成功 APP build：

1. 先构建到独立 `artifacts/publish-*`；
2. 运行 Core、布局回归、UI smoke、安装包和 CAD 相关验收；
3. 正常关闭正在运行的 `release` APP，不强杀，不丢未保存工作；
4. 复制并保留用户设置、词库、任务和回滚数据；
5. 用 `D:\DWGC2E\tools\Publish-Desktop.ps1`（不带 `-BuildOnly`）更新 `D:\DWGC2E\release`；
6. 校验安装后 EXE SHA-256；
7. 只保留最新候选和一个回滚版本；
8. 如果 release 被占用或验证失败，保持旧 release，不把 artifacts 冒充成已安装版本。
