# 支付异常处理、发布与回滚手册

## 强制安全边界

- 未取得单独授权，不创建真实支付订单、不扫码付款、不创建验收账号、不启用收费服务。
- 不因二维码过期、用户隐藏、网络错误或 24 小时未收到回调将订单改成失败。
- 不修改已用额度，不删除交易或结算流水，不直接改数据库将订单设为 paid。
- 当前 inspect 的未认证平台查询仅供诊断；截图和客户端“已付款”声明均不能驱动结算。
- 管理凭证只能在受控运维端使用。网站代理不开放支付管理接口；不能把 ADMIN_API_KEY 放进网页或 APP。

## 每笔异常的操作流程

1. 从已认证 recovery 清单取得订单号；超过 5 分钟的未确认订单及回调冲突均需分配内部工单和责任人。
2. 用 GET orders/:no/review 查询状态与事件；使用 before 游标读取更早事件。不得在公开工单粘贴密钥、签名、完整回调 URL、付款码或用户私密资料。
3. 在支付商户后台核对商户、平台交易号、商户订单号、支付通道、金额（整数分）及真实付款状态。弱查询只能辅助定位，不能作为凭证。
4. 将证据保存在访问受控的工单系统；审计记录只写证据引用，不上传原始敏感截图。
5. POST review，字段 operator=负责操作人员的内部标识、evidenceRef=工单／证据编号、outcome 为 awaiting_provider、provider_replay_requested 或 escalated。此接口返回 settled=false。
6. 确认平台已支付但本地未结算：联系支付平台重发合法签名回调；只有正常验签和事务结算通过才到账。不要人工“强制成功”。
7. 交易号／金额冲突：维持新下单关闭，升级核实；不能通过换交易号、改金额或删流水绕过唯一性检查。
8. 24 小时仍无可信结论的任务保留 manual；人工工单持续跟踪。当前不支持凭截图或未认证查询直接关闭未知订单并再次购买。
9. 恢复后复核：订单 paid，恰好一笔金额／交易号匹配的结算，会员延长正确、已用量未清空，双端一致快照正确。

共享管理凭证只能证明管理权限，operator 是操作者显式登记的审计信息；如需不可抵赖的个人操作身份，应另行接入个人管理员身份系统，不把本期接口当作该能力已完成。

## 回滚

1. 第一动作：PAYMENTS_ENABLED=false，必要时清空 PAYMENTS_TEST_USERS，阻止新下单；保留回调与订单查询。
2. 固定异常工单和脱敏证据。不要恢复旧数据库备份覆盖生产，不撤销迁移新增流水。
3. 优先前向修复。旧 Worker 的结算守卫／二维码前置判断不兼容早到回调，不能盲目回滚到旧支付逻辑；仅部署已验证兼容新增表和交易数据的代码。
4. 网站可回滚兼容前端，但必须保留待完成购买记录和停购提示。不能通过清理浏览器存储解决不明订单。
5. APP 候选包不覆盖当前运行的 release；正式发行后如需回滚，保留用户账户数据和购买意图。下载入口只能指向对应已验收发行包。
6. 回滚后复验回调、查询、任务租约、金额唯一性及幂等重试，不以 HTTP 200 代替到账核验。
