# Installed APP reader / real CAD round-trip probe

This standalone .NET 8 probe loads `DwgTranslator.Core.dll` and its managed dependencies **from the installed single-file APP executable**. It does not rebuild/reference the Core project and does not launch the APP UI. The bundled assemblies are read into memory; installed files are unchanged. `InstalledBundle` supports the installed .NET bundle 6.0 format only, with bounded entry checks and decompression length validation.

Use a synthetic source generated by `tests/CadIntegration/Test-CadRuntimeWriteback.ps1` (six DBText/MText entries). Run `dotnet run --project tests/CadRuntimeProbe -c Release -- prepare RELEASE SOURCE_DWG NEW_EVIDENCE_DIRECTORY`. It validates source extraction and writes `writeback.json` with deterministic replacement text and metadata produced by the actual APP reader. Then run the release CAD plugin's `DwgTranslateWrite` in the real CAD host with that config path. Finally run the same probe with `verify` instead of `prepare` and the same paths.

The probe records source/output extraction and assembly/executable hashes, requires an exact session-specific 6/0 completion signal, and checks original hash, output text, entity count/handles/types/rotations and source-file attribution. `prepare` refuses an existing evidence directory. The CAD script/launch is a separate explicit step; do not use a user drawing or rerun while an owned CAD process is still alive.

This covers installed-reader -> actual CAD -> installed-reader, **not** APP UI scheduling, cloud translation, billing, real-account synchronization, or all CAD entity types. It is a test utility build, not an APP build or release delivery.

Initial September 16 evidence `cad-runtime/reader-roundtrip` found width codes leaking into PlainText (for example `W0.75;`); the failed verification log is retained. Fixed-release acceptance uses a distinct directory and never overwrites the original failure evidence.

Fixed-release outcome: `2.1.1+ui.20260916-163249.a3f6f1f` completed the real reader/CAD/reader round-trip, six entities with exact text, stable handles/types/rotations, unchanged source, correct output attribution and no temporary DWG leak. Evidence: `cad-runtime/reader-roundtrip-fixed/verification.json` and `reader-verify-fixed.log`. Ten permanent reader regression cases cover numeric width cleanup, raw format preservation and unchanged decoding of other controls. The narrow production fix is in the reader adapter, not the CAD writer/layout algorithm. Prior failure evidence remains under `reader-roundtrip`.

### Historical production-path correction (before the test window)

The APP's ApiClientFactory forces `worker`, and App.xaml.cs constructs TaskManager with WorkerTranslationService. That adapter explicitly writes entity text/status. Thus the original `pipeline` failure is a **legacy/local-constructor contract bug**, not evidence of the same defect in the normal production queue. Do not describe it as a verified production P0 or change core logic on that basis.

Added `worker-pipeline RELEASE SOURCE_DWG NEW_EVIDENCE_DIRECTORY` to exercise installed WorkerApiClient + WorkerTranslationService + TaskManager, with installed format restoration and real CAD interop. Only HTTP is replaced by an in-memory handler: it checks endpoint/method/session/idempotency header/language direction/six item IDs and returns fixed translation JSON. No network, production account, payment, or real Worker execution is involved. It requires zero local-model calls, one HTTP batch, one CAD writeback, six exact output labels and persisted completion. This mode and the new regression remain **uncompiled/unexecuted during the release freeze**. Existing `pipeline` mode is retained to reproduce the local-branch failure separately.
